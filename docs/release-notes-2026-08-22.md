# What's New — August 22, 2026

Two payroll fixes today: payslips now show the correct itemized earnings breakdown on weeks that include a worked holiday or a worked rest day (gross and net pay were never wrong, only the line items above them); and overtime that crosses midnight now pays the correct number of minutes instead of an inflated one, with a new safety cap that catches implausible punch spans before they turn into pay.

---

## Payroll / Attendance

### Payslip breakdown fixed for worked holidays and rest days

An employee's payslip lists earnings as separate lines — Basic Pay, Overtime, Holiday Pay, Incentive, Paid Leave — that are supposed to add up to GROSS PAY. On any week where the employee worked a holiday or a rest day, they didn't: Basic Pay was quietly short by that day's base wage, even though GROSS PAY and the employee's actual take-home NET PAY were both correct the whole time. Nobody was underpaid — the payslip just displayed the earnings breakdown incorrectly.

**A real example that surfaced the bug**: an employee on a ₱550 daily rate worked all 6 days of the period, and the last day happened to be a special (non-working) holiday. Basic Pay should be ₱3,300.00 (₱550 × 6 days worked). The payslip instead showed **₱2,750.00** (₱550 × 5 days) — the worked holiday's ₱550 base wage had vanished from the breakdown, even though it was still correctly included in GROSS PAY. The line items were short by exactly ₱550 and no longer summed to the gross total shown right below them.

The cause: the payslip computed "Basic Pay" by multiplying the daily rate by a day-count column (`total_regular_days`) that is deliberately defined to *exclude* worked holidays and rest days (those days get their own holiday-pay treatment elsewhere in the system). That exclusion is correct for what that column is used for internally — but the payslip was using it to reconstruct a peso amount, and reconstructing pay from an incomplete day count understated it.

The fix: the payslip no longer multiplies a day count by the daily rate to get Basic Pay. It now starts from GROSS PAY — the one number that was always correct — and subtracts out Overtime, Holiday Pay, and Incentive (which already have their own lines), adding back Late/Undertime/Fine penalties (which already appear as their own negative lines further down, so they'd otherwise be subtracted twice), and subtracting Paid Leave (which also has its own line). What's left is the true Basic Pay, and it now always reconciles with GROSS PAY.

The payslip's attendance summary strip also gets a new **"Days Paid"** figure alongside the existing **"Regular"** day count, so the "Basic Pay (Nd)" label shows the actual number of days that earned base pay (worked days including holidays and rest days, excluding only paid-leave days, which are shown separately) instead of the narrower internal count.

### Overtime spanning midnight no longer overpays

When an employee's overtime shift runs past midnight, their "OT Out" punch gets stamped with the *same date* as their "OT In" punch — the system doesn't know the clock rolled over to a new day. The overtime calculation was measuring the gap between those two timestamps as if both happened on the same day, which for an overnight shift means counting backwards almost a full 24 hours instead of forward a few hours.

**A real example that surfaced the bug**: an employee on a ₱525 daily rate clocked overtime in at 7:58 PM and out at 1:15 AM — a real span of 5 hours 17 minutes (317 minutes). Because both punches carried the same calendar date, the system computed the gap as 18 hours 43 minutes (1,123 minutes) instead. That inflated 1,123 minutes turned into ₱1,535.35 of overtime pay and a ₱2,040.35 total for the day. The correct numbers are 317 minutes, ₱433.40 of overtime pay, and ₱938.40 for the day.

The fix: when the "OT Out" timestamp is earlier in the day than the "OT In" timestamp, the system now recognizes that as a midnight rollover and rolls the "OT Out" time forward to the next day before measuring the gap — so 7:58 PM to 1:15 AM correctly reads as roughly 5 hours, not 19. As a backstop, any overtime span that still comes out implausibly long (more than 12 hours by default, adjustable) is no longer paid automatically — the raw punch data is kept on the record for a manager to review, but the pay is withheld and the day is flagged until someone verifies what actually happened. This protects against the *next* bad punch, not just this one.

### Notes for reviewers

- `payroll/Attendance/Services/AttendanceService.php` (`processDailyAttendance`) — the `OVERTIME_IN`/`OVERTIME_OUT` diff no longer uses `abs()`. When the OT-out timestamp is earlier than the OT-in timestamp, it's rolled forward one day (`addDay()`, assigned rather than mutated — `CarbonImmutable` is in effect app-wide) before diffing.
- New config key `payroll.max_overtime_minutes` (env `PAYROLL_MAX_OVERTIME_MINUTES`, default `720`), resolved through `PayrollSettingService` first with the config value as fallback — same pattern as `half_day_threshold_minutes`. A post-rollover span exceeding the cap sets `overtime_pay = 0` and `overtime_multiplier = null` while still recording the raw `overtime_minutes`, and forces `is_incomplete = true` with a reason ending in `"verify punches"`. An earlier incomplete reason (e.g. a missing lunch punch) is preserved rather than overwritten (`??=`).
- `payroll/Attendance/Services/PayrollPeriodService.php` (`findIncompleteSheets`) — applies the identical rollover + cap check against the period's already-fetched punches so an over-cap day surfaces in the Check Payroll report, not just on the individual attendance sheet. `max_overtime_minutes` is resolved once before the loop, and no new query was added per row or per sheet — the `< 150` query-count regression test on `PayrollPeriodService::generate` still passes.
- Scope was deliberately narrow: this does **not** change which calendar day a punch is attributed to (`whereDate('timestamp', $date)` in `AttendanceService`, or `TimeLogService::punch`'s date assignment are untouched), and does not add night-shift support — the business has none. Only the OT-out/OT-in diff itself was corrected.
- New test file `tests/Feature/Payroll/AttendanceOvertimeMidnightTest.php` (5 tests): the exact reported scenario (317 minutes, 1.25x, ₱433.40); a regression guard confirming an ordinary same-day OT span (e.g. 6 PM–8 PM) is unaffected; an over-cap span withholding pay and flagging the sheet; the `??=` behavior keeping an earlier "Lunch return punch missing" reason instead of overwriting it; and a configurable-cap check via `PayrollSettingService`.
- Full suite (`php artisan test`) passes at 512 tests / 2,372 assertions after this change — no existing test encoded the old backwards-diff behavior, so nothing needed to be rewritten.
- Docs: `docs/payroll.md` §3.4 ("Overtime Pay") rewritten to match the code as it actually is today — OT punches are the *primary* source (an approved `OvertimeRequest` is a fallback used only when no OT punch pair exists that day), there is no "lower-of-two" reconciliation and no 60-minute minimum, and the section now documents the midnight-rollover rule and the `max_overtime_minutes` cap. Those stale claims predated this fix and were not introduced by it.
